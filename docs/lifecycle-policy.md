# 파일 전(全) 주기 정책 — 생성·유통·폐기·파기 (Lifecycle Policy v0.1)

> "폐기"라는 말에 서로 다른 세 가지가 섞여 쓰인다. LM은 이를 분리해
> 정의한다. 혼동은 곧 사고다: 폐기된 민감문서가 공개되거나,
> 보존 의무가 있는 기록이 조기에 소멸된다.

## 1. 상태 모델

```
        발급(ISSUE)ㅡㅡㅡㅡㅡㅡㅡㅡㅡㅡㅡㅡㅡㅡㅡㅡㅡㅡㅡ┐
          │                                        │
          ├─ 파생(DERIVE) ── 새 문서의 발급 (계보 연결)  │
          │                                        │
          ├─ 등급변경(REGRADE) ── 상향 즉시 / 하향 승인   │ 유통 중
          │     └─ S→O 하향 = "공개 전환" (의도적 행위)  │
          │                                        │
        폐기(REVOKE) ── 유통 정지. 비밀성 유지. 가역.  ←──┘
          │
        [Phase 2] 파기(DESTROY) ── 보존기간 만료 + 심의 후.
              키 파기(crypto-shredding). 불가역. 원장 증적은 영구.
```

모든 전이는 원장 이벤트 행 추가로만 표현된다(불변식 1). 어떤 상태도
원장에서 지워지지 않는다 — "무엇이 존재했고 언제 어떻게 됐는가"가 증적이다.

## 2. 세 가지 전이의 구분 — 질문에 대한 답

| | 폐기 (REVOKE) | 공개 전환 (REGRADE S→O / 시한부) | 파기 (DESTROY, Phase 2) |
|---|---|---|---|
| 의미 | 이 라벨·문서는 더 이상 유효하지 않다 | 비밀성이 해제되었다 | 내용에 다시는 접근할 수 없어야 한다 |
| 전형적 사유 | 오분류, 신규 버전으로 대체, 업무 종료 | 시한 도래(disclosureCondition), 심사 후 하향 | 보존기간 만료 + 기록물 파기 심의 의결 |
| 게이트 효과 | 통행 거부 (revoked → deny) | O등급 규칙으로 통행 | 문서 실물이 존재하지 않음 |
| 본문 비밀성 | **유지** — 폐기가 공개를 뜻하지 않는다 | 해제 | 키 파기로 영구 봉인 |
| 복호화 키 | **유지** | (O등급은 애초 미암호화) | **파기 (crypto-shredding)** |
| 가역성 | 가역 — 재발급 가능 | 절차적으로 가역(재상향은 즉시) | **불가역** |
| 승인 | 발급 권한 | 하향 승인 토큰 (T9) | 기록물 파기 심의 (별도 거버넌스) |

**Q. 폐기된 파일은 공개로 전환되어야 하나? — 아니다.**
폐기는 "무효화"이지 "비밀 해제"가 아니다. 폐기 사유의 대부분(오분류,
구 버전 대체)은 본문이 여전히 민감하다. 공개 전환은 오직 두 경로뿐이다:
① 승인 토큰을 동반한 REGRADE S→O, ② 라벨의 `disclosureCondition`
(시한부 공개 전환일) 도래 시의 **재분류 절차**(자동 공개가 아니라
절차 개시 신호다). 폐기가 공개를 유발하는 경로는 존재하지 않는다.

**Q. 복호화 키를 제거하고 아무도 못 보게 해야 하나? — "파기" 단계에서만.**
키 파기(crypto-shredding)는 올바른 파기 **수단**이지만, 폐기(REVOKE)에
결합하면 안 된다:
- 폐기는 가역이어야 한다 — 오분류로 폐기한 문서를 재발급할 때 본문이
  필요하다.
- 공공기록물은 보존기간 전 임의 파기가 금지되며, 파기는 심의 절차를
  거친다. 라벨 폐기 권한과 기록물 파기 권한은 서로 다른 거버넌스다.
- 소송·감사 보류(legal hold) 중인 문서는 폐기되어도 파기할 수 없다.

## 3. 파기(DESTROY) 설계 — Phase 2 규격

서버는 본문을 저장하지 않으므로(불변식 3), LM의 파기는 두 동작이다:

1. **키 파기 지시**: KMS의 해당 문서 DEK(데이터 암호화 키)를 파기한다.
   - 전제: **문서별 DEK** (KMS KEK로 래핑). 공용 키 하나로 전체를
     암호화하면 개별 파기가 불가능하다 — S등급 본문 암호화 구현 시
     반드시 문서별 키로 설계할 것 (crypto.Cipher 사용 규칙).
   - O등급(미암호화)의 실물 삭제는 ECM/저장소의 책임이며, LM은 증적만 기록.
2. **원장 파기 이벤트**: `DESTROY` 이벤트 행 추가 (event_type 확장,
   revoked_ref → 원 발급 seq, reason → 파기 심의 근거).
   - 해시·메타데이터·계보는 **영구 보존**된다 — 파기 후에도 "그 문서가
     존재했고 언제 파기됐는지"는 증명 가능해야 한다. 이는 개인정보의
     내용 파기와 모순되지 않는다(원장에는 본문이 없다).

파기 후 검증 의미론: 해당 해시 제시 시 `revocation: "revoked"` 계열에
`reasons: ["destroyed"]` — 파기된 문서의 사본이 유통되면 게이트가
차단할 근거가 된다(파기는 사본 회수까지 보장하지 못하므로, 원장 증적이
사본 탐지의 근거가 된다).

## 4. Phase 1 구현 현황

| 전이 | 상태 |
|---|---|
| 발급·파생 | ✔ 웹 "생성/폐기" 탭, lm issue/scan |
| 등급변경 (공개 전환 포함) | ✔ 웹 수명주기 조치, lm regrade (하향 승인 토큰 T9) |
| 폐기 | ✔ 웹 수명주기 조치, lm revoke — REVOKE 이벤트 |
| 시한부 공개 전환 | ✔ 검증이 disclosureCondition 도래를 감지해 재분류 권고(reasons + review) — 재분류 절차 자동화는 Phase 2 |
| 파기 | ✔ DESTROY 이벤트·파기 심의 토큰(LM_DESTROY_TOKEN)·검증 destroyed/deny·웹·lm destroy — **KMS 키 파기 지시는 인터페이스(crypto.KeyShredder)만, 연동은 Phase 2** |
